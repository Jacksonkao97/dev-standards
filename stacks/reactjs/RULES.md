# React 19 + Vite 8 Engineering Standards

Complete coding style, configuration, and architectural rules for client-side React 19 + Vite 8 SPA projects. These rules extend [`common/BASE_RULES.md`](../../common/BASE_RULES.md).

---

## 1. Mandatory Freshness & Breaking-Change Check (Pre-Coding Gate)

> **STOP & VERIFY BEFORE SCAFFOLDING OR CODING.**

Before running `create-vite`, upgrading dependencies, or writing feature code:

1. **Check installed versions and release notes**: inspect `package.json` and verify the current releases of `create-vite`, `vite`, `react`, `@vitejs/plugin-react`, `@tailwindcss/vite`, `typescript`, and `oxlint`.
2. **Check CLI & ecosystem drift**: verify `npx --yes create-vite@latest --help`, Vite 8 + `@vitejs/plugin-react` React Compiler support (including whether Oxc-native `oxc-transform-react` + `react({ compiler: true })` has graduated from experimental to replace the Babel preset), Tailwind CSS v4 Vite plugin integration, and Oxlint config/rules.
3. **If anything changed, deprecated, or conflicts/breaks against these rules**:
   - **STOP before coding.**
   - Explain clearly what changed (documented rule vs. current framework/CLI behavior).
   - Provide a concrete recommendation for the active project.
   - Ask the user how to proceed, and offer to update `Jacksonkao97/dev-standards`.

## 2. Toolchain & Core Defaults

| Layer | Standard |
| --- | --- |
| Package manager | `npm` |
| Framework & build | React 19 + Vite 8 (Rolldown bundler + Oxc compiler) |
| React Compiler | Enabled via `create-vite`'s `react-compiler-ts` template (`@rolldown/plugin-babel` + `babel-plugin-react-compiler` + `reactCompilerPreset()`) |
| Language | TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`, relative `paths` with no `baseUrl`) |
| Path alias | `@/*` -> `./src/*` |
| Linter | **Oxlint** (`.oxlintrc.json`) with native Rust plugins (`typescript`, `react`, `jsx-a11y`, `import`, `oxc`) |
| Formatter | **Prettier** (`.prettierrc`) + `prettier-plugin-tailwindcss` (`tailwindStylesheet: "./src/index.css"`) |
| Validation | `zod` |
| Icons & styling | Tailwind CSS v4 (`@tailwindcss/vite`) + `lucide-react` |

### Vite Configuration (`vite.config.ts`)

Preserve the React Compiler plugin setup generated by `create-vite` (`react-compiler-ts`), add Tailwind CSS v4 (`@tailwindcss/vite`), and configure an explicit `resolve.alias` so `@/*` resolves identically across Vite dev/build, CSS, and Vitest:

```ts
import { fileURLToPath, URL } from "node:url";
import babel from "@rolldown/plugin-babel";
import tailwindcss from "@tailwindcss/vite";
import react, { reactCompilerPreset } from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [react(), babel({ presets: [reactCompilerPreset()] }), tailwindcss()],
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
});
```

**React Compiler & TypeScript 7 notes:**

- **Automatic memoization**: with React Compiler enabled, do not hand-write `useMemo`, `useCallback`, or `React.memo` by default; reserve manual memoization only for profiled hot spots or effect-dependency escape hatches.
- **Native Oxc compiler watch item**: `@vitejs/plugin-react` 6.1+ also offers experimental Rust-native React Compiler support via `oxc-transform-react` (`react({ compiler: true })`). Check its stability during Step 0 when starting new projects.
- **No `baseUrl` in TypeScript 7+**: TypeScript 7 removed `baseUrl` (hard error). Define `"paths": { "@/*": ["./src/*"] }` directly relative to the tsconfig file in `tsconfig.app.json` (and mirror `compilerOptions.paths` in root `tsconfig.json` if an external CLI such as `shadcn/ui` inspects the root config).

## 3. Feature-Based Hybrid Folder Architecture & Rule of Two

Organize code under `src/` using a feature-based hybrid structure that works cleanly both before and after client-side routing is added:

```text
src/
├── main.tsx                 # App mount point (safely guards #root without `!`)
├── app.tsx                  # Root application shell (named export App)
├── index.css                # Tailwind CSS v4 entry (@import "tailwindcss";)
├── routes/                  # Added on demand if TanStack Router is installed (keep route files thin)
├── features/
│   └── <feature>/
│       ├── components/      # Components used by THIS feature only
│       ├── hooks/           # Hooks used by THIS feature only
│       └── lib/             # Helpers, schemas, API functions for THIS feature only
├── components/              # Shared components across 2+ features
│   └── ui/                  # Added on demand if shadcn/ui is installed
├── hooks/                   # Shared React hooks across 2+ features
├── lib/                     # Shared utilities, env schema, HTTP/API client helpers
└── types/                   # Shared TypeScript types
```

### The Rule of Two

- **Used by 1 feature only**: keep inside `src/features/<feature>/components/`, `hooks/`, or `lib/`.
- **Used by 2 or more features**: promote to top-level `src/components/`, `src/hooks/`, `src/lib/`, or `src/types/`.
- **No cross-feature private imports**: never import from another feature's `components`, `hooks`, or `lib` directory. If a second feature needs it, promote it first.

### TanStack Router Folder Caveats (When Added On Demand)

- Keep route files under `src/routes/` thin—wire params, search validation, loaders, and layout composition, while keeping domain UI/logic inside `src/features/<feature>/`.
- Unlike Next.js (which uses `_` for private folders), TanStack Router's file-based routing treats `_`-prefixed folders as **pathless layout routes** and uses a `-` prefix (e.g., `-components/`) to ignore colocated files.
- When TanStack Router generates `src/routeTree.gen.ts`, add `"src/routeTree.gen.ts"` to `.oxlintrc.json` `ignorePatterns` and `.prettierignore`.

## 4. Styling & UI

- **Lean default**: **Tailwind CSS v4** (`@tailwindcss/vite` + `@import "tailwindcss";` in `src/index.css`) + **`lucide-react`** for icons.
- **Add UI primitives only on demand**: do not pre-install component libraries during bootstrap. Add `shadcn/ui` (into `src/components/ui/`) or headless accessible primitives (e.g., Base UI / Radix) only when the product requires complex interactive widgets such as dialogs, comboboxes, menus, popovers, or date pickers.
- **Class ordering**: rely on `prettier-plugin-tailwindcss` (`tailwindStylesheet: "./src/index.css"`) to keep Tailwind utility classes consistently sorted.

## 5. Routing, Data Fetching, State & Boundaries

### Client-Side Routing

- **Lean bootstrap**: do not pre-install a router for single-view SPAs or widgets.
- **Standard on demand**: standardize on **TanStack Router** (`@tanstack/react-router`) when multi-page navigation is needed, leveraging end-to-end typed routes and Zod-validated URL search params.

### Remote Data Fetching & Mutations

- **Avoid ad-hoc `useEffect` data fetching**: do not hand-roll loading/error/race-condition state inside `useEffect`.
- **Standard on demand**: standardize on **TanStack Query** (`@tanstack/react-query`) as soon as the app fetches or mutates remote API data (caching, deduplication, retries, optimistic updates, and invalidation).
- **Validate API boundaries with `zod`**: treat every external API response, form payload, and URL search param as untrusted and parse it with `zod` before using it in UI state.
- **Explicit boundary errors**: return a typed discriminated union or raise typed API error classes instead of swallowing failures silently:

```ts
export type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; status?: number };
```

### Client State Management

- **URL search params & local React state first**: model shareable filters, pagination, tabs, and sorting in URL search params; keep ephemeral UI state in local React state (`useState`, `useReducer`).
- **External client state only when justified**: add **Zustand** only when complex cross-tree client state genuinely demands it.

### Client-Side Environment Variables & Secret Hygiene

- **Zero secrets in `VITE_*`**: every `VITE_*` variable is statically embedded into the public client JavaScript bundle. **Never** put API secrets, private tokens, signing keys, or database credentials in `VITE_*` variables or frontend code.
- **Centralized validation**: validate public runtime config once in `src/lib/env.ts` with **`zod`** instead of scattering raw `import.meta.env.*` reads across components:

```ts
import { z } from "zod";

const envSchema = z.object({
  VITE_API_BASE_URL: z.url(),
});

export const env = envSchema.parse(import.meta.env);
```

## 6. Backend API, Authentication & Deployment

- **Intentionally NOT locked in global standards.**
- Choose the backend API architecture, authentication provider, and static/CDN host per project during `/plan`.
- **SPA security & hosting defaults**:
  - Never treat client-side route guards or hidden UI controls as authorization—always enforce authentication and permissions on the backend API.
  - Prefer `HttpOnly` cookie sessions or OAuth 2.0 + PKCE flows over storing sensitive long-lived tokens in `localStorage`.
  - When client-side routing is enabled, configure the static host to rewrite unknown paths to `index.html` for deep links.

## 7. TypeScript & Naming Conventions

### File Naming

- Use **`kebab-case`** for all files and folders (e.g., `app.tsx`, `invoice-table.tsx`, `use-debounce.ts`, `format-currency.ts`).
- **Exception**: tool/build config files (`vite.config.ts`) and framework-generated or reserved conventions when added on demand (e.g., TanStack Router's `__root.tsx` and `routeTree.gen.ts`).

### Symbol Naming

| Construct | Convention | Example |
| --- | --- | --- |
| React components & TS types | `PascalCase` | `OrderSummary`, `ApiResult` |
| Functions, hooks, variables | `camelCase` | `formatCurrency`, `useDebouncedValue` |
| Module-level constants | `UPPER_SNAKE_CASE` | `MAX_UPLOAD_BYTES`, `DEFAULT_PAGE_SIZE` |

### Exports, Types & Functions

- **Named exports everywhere**: use named exports for components (including `export function App()` in `src/app.tsx`), hooks, utilities, and types. Only use `export default` where a tool or config file requires it (`vite.config.ts`).
- **Prefer `type` over `interface`**: use `type` aliases consistently (reserve `interface` only when module augmentation / declaration merging is required).
- **Zero `any`**: never use `any`. Use `unknown` plus narrowing or `zod` parsing.
- **Explicit `import type`**: use `import type { ... }` for type-only imports (also enforced by `verbatimModuleSyntax: true` and Oxlint).
- **`noUncheckedIndexedAccess` discipline**: treat indexed array/record access and DOM lookups as `T | undefined` / `T | null` and narrow safely instead of scattering non-null assertions (`!`).
- **Function declarations**: use `function` declarations for top-level React components and helper functions (`export function UserCard(...) {}`).

## 8. Testing Strategy

- **Lean bootstrap**: do not pre-install test runners or boilerplate test suites during project bootstrap.
- **Standard test stack when added**:
  - **Vitest** for unit and integration tests (paired with React Testing Library when component DOM tests are needed).
  - **Playwright** for end-to-end (E2E) browser tests.
- Once tests exist in a repository, they become part of the Definition of Done and must pass before claiming completion.

---

## 9. Verification & Definition of Done

Before committing or claiming work is done, run the full check script and verify exit code `0`:

```bash
npm run check
# Runs: npm run typecheck && npm run lint && npm run format:check && npm run build
```

If tests are configured in the project, run them as well and verify all pass.

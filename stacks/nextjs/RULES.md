# Next.js 16+ Engineering Standards

Complete coding style, configuration, and architectural rules for Next.js 16+ App Router projects. These rules extend [`common/BASE_RULES.md`](../../common/BASE_RULES.md).

---

## 1. Mandatory Freshness & Breaking-Change Check (Pre-Coding Gate)

> **STOP & VERIFY BEFORE SCAFFOLDING OR CODING.**

Before running `create-next-app`, upgrading Next.js, or writing feature code:

1. **Check installed versions and bundled Next.js docs**: inspect `package.json` and read the relevant guides in `node_modules/next/dist/docs/` (Next.js ships version-exact documentation inside `node_modules`).
2. **Check CLI & ecosystem drift**: verify `npx create-next-app@latest --help`, Next.js release notes, Oxlint config/rules, and Tailwind CSS v4 integration when bootstrapping or upgrading.
3. **If anything changed, deprecated, or conflicts/breaks against these rules**:
   - **STOP before coding.**
   - Explain clearly what changed (documented rule vs. current framework/CLI behavior).
   - Provide a concrete recommendation for the active project.
   - Ask the user how to proceed, and offer to update `Jacksonkao97/dev-standards`.

## 2. Toolchain & Core Defaults

| Layer | Standard |
| --- | --- |
| Package manager | `npm` |
| Framework | Next.js 16+ (App Router, `src/` directory) |
| Bundler | Turbopack (default in Next.js 16+) |
| Language | TypeScript with `strict: true` and `noUncheckedIndexedAccess: true` |
| Path alias | `@/*` -> `./src/*` |
| Linter | **Oxlint** (`.oxlintrc.json`) with native Rust plugins |
| Formatter | **Prettier** (`.prettierrc`) + `prettier-plugin-tailwindcss` (`tailwindStylesheet: "./src/app/globals.css"`) |
| Validation & guards | `zod` + `server-only` |
| Icons & styling | Tailwind CSS v4 + `lucide-react` |

### Next.js Configuration (`next.config.ts`)

Enable these top-level defaults while preserving any bundler rules generated by `create-next-app` (such as `@tailwindcss/turbopack`):

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  reactCompiler: true,
  typedRoutes: true,
  // Preserve generated turbopack/loader rules when present
};

export default nextConfig;
```

**Required Cache Components caveats:**

- **Static export (`output: "export"`)**: if a project targets static hosting with `output: "export"`, **disable `cacheComponents` (and `partialPrefetching`)**.
- **No `runtime` route segment exports**: while `cacheComponents: true` is active, **never export `runtime`** (not even `export const runtime = "nodejs"` or `"edge"`). Cache Components requires the Node.js runtime and rejects `runtime` segment exports.
- **Explicit caching & streaming**: with Cache Components, request-time data fetching is dynamic by default. Wrap dynamic subtrees in `<Suspense>` boundaries and opt in to caching explicitly via `"use cache"`, `cacheLife`, and `cacheTag`. Check `node_modules/next/dist/docs/` for current caching APIs before implementing.

## 3. Hybrid Folder Architecture & Rule of Two

Organize code under `src/` using a hybrid structure that keeps route-local code colocated without duplicating shared abstractions:

```text
src/
├── app/
│   ├── layout.tsx
│   ├── globals.css
│   ├── page.tsx
│   ├── api/                 # Route Handlers only (webhooks, callbacks, external APIs)
│   └── <route>/
│       ├── page.tsx
│       ├── _components/     # Components used by THIS route only
│       ├── _hooks/          # Hooks used by THIS route only
│       └── _lib/            # Helpers, schemas, Server Actions for THIS route only
├── components/              # Shared components across 2+ routes
│   └── ui/                  # Added on demand if shadcn/ui is installed
├── hooks/                   # Shared React hooks across 2+ routes
├── lib/                     # Shared utilities, env schema, server helpers
└── types/                   # Shared TypeScript types
```

### The Rule of Two

- **Used by 1 route only**: keep inside `src/app/<route>/_components/`, `_hooks/`, or `_lib/`.
- **Used by 2 or more routes**: promote to top-level `src/components/`, `src/hooks/`, `src/lib/`, or `src/types/`.
- **No cross-route private imports**: never import from another route's `_components`, `_hooks`, or `_lib` directory. If a second route needs it, promote it first.

## 4. Styling & UI

- **Lean default**: **Tailwind CSS v4** (`@import "tailwindcss";` in `src/app/globals.css`) + **`lucide-react`** for icons.
- **Add UI primitives only on demand**: do not pre-install component libraries during bootstrap. Add `shadcn/ui` (into `src/components/ui/`) or headless accessible primitives (e.g., Base UI / Radix) only when the product requires complex interactive widgets such as dialogs, comboboxes, menus, popovers, or date pickers.
- **Class ordering**: rely on `prettier-plugin-tailwindcss` to keep Tailwind utility classes consistently sorted.

## 5. Data Fetching, Mutations & State

### Server-First Rendering

- **Server Components are the default**: fetch data, read secrets, and format server payloads in Server Components.
- **Minimize client bundles**: push `"use client"` down to the smallest interactive leaf component. Avoid turning entire page trees or layouts into Client Components.

### Mutations via Server Actions

- Use Server Actions (`"use server"`) for internal application mutations.
- Always validate untrusted inputs with **`zod`** and verify authentication/authorization on the server before mutating state.
- Return a typed discriminated union instead of throwing expected validation/domain errors across the client boundary:

```ts
export type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; fieldErrors?: Record<string, string[]> };
```

### Route Handlers (`src/app/api/`)

- Reserve Route Handlers for **webhooks, OAuth callbacks, health checks, and external HTTP APIs** consumed by third parties or non-React clients.
- Prefer Server Components for reads and Server Actions for internal form/UI mutations.

### State Management

- **URL search params & local React state first**: model shareable filters, pagination, tabs, and sorting in URL search params; keep ephemeral UI state in local React state (`useState`, `useReducer`).
- **External client state only when justified**: add Zustand or TanStack Query only when complex cross-tree client state or client-driven polling/optimistic cache sync genuinely demands it.

### Server Isolation & Environment Variables

- Mark server-only modules (database clients, secret SDKs, internal signing/token helpers) with `import "server-only";` at the top of the file so client imports fail at build time.
- Validate environment variables with **`zod`** in a centralized module (e.g., `src/lib/env.ts` with `import "server-only";` for server secrets, and a separate public schema for `NEXT_PUBLIC_*` variables). Never scatter unvalidated `process.env.*` reads across the codebase.

## 7. TypeScript & Naming Conventions

### File Naming

- Use **`kebab-case`** for all files and folders (e.g., `invoice-table.tsx`, `use-debounce.ts`, `format-currency.ts`).
- **Exception**: Next.js reserved file conventions and framework config files (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `global-error.tsx`, `not-found.tsx`, `route.ts`, `default.tsx`, `template.tsx`, `proxy.ts`, `next.config.ts`, `instrumentation.ts`, etc.).

### Symbol Naming

| Construct | Convention | Example |
| --- | --- | --- |
| React components & TS types | `PascalCase` | `OrderSummary`, `ActionResult` |
| Functions, hooks, variables | `camelCase` | `formatCurrency`, `useDebouncedValue` |
| Module-level constants | `UPPER_SNAKE_CASE` | `MAX_UPLOAD_BYTES`, `DEFAULT_PAGE_SIZE` |

### Exports, Types & Functions

- **Named exports everywhere**: use named exports for components, hooks, utilities, and types. Only use `export default` where Next.js requires it (route files like `page.tsx`, `layout.tsx`, `error.tsx`, `not-found.tsx`, and config files like `next.config.ts`).
- **Prefer `type` over `interface`**: use `type` aliases consistently (reserve `interface` only when module augmentation / declaration merging is required).
- **Zero `any`**: never use `any`. Use `unknown` plus narrowing or `zod` parsing.
- **Explicit `import type`**: use `import type { ... }` for type-only imports.
- **`noUncheckedIndexedAccess` discipline**: treat indexed array/record access as `T | undefined` and narrow safely instead of scattering non-null assertions (`!`).
- **Function declarations**: use `function` declarations for top-level React components and helper functions (`export function UserCard(...) {}`).

## 8. Testing Strategy

- **Lean bootstrap**: do not pre-install test runners or boilerplate test suites during project bootstrap.
- **Standard test stack when added**:
  - **Vitest** for unit and integration tests.
  - **Playwright** for end-to-end (E2E) browser tests.
- Once tests exist in a repository, they become part of the Definition of Done and must pass before claiming completion.

---

## 9. Verification & Definition of Done

Before committing or claiming work is done, run the full check script and verify exit code `0`:

```bash
npm run check
# Runs: npm run typecheck && npm run lint && npm run format:check && npm run build
```

If tests are configured in the project, run them as well and verify all pass.
